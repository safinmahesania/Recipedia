# Repository hygiene

## What the audit of the repo found

| Issue | Size | Why it matters |
|---|---|---|
| `out/` is tracked, 10 files | **7.5 MB of 15 MB** | every file is regenerated by a script; committing them makes every clone pay forever |
| Two `import_wikibooks` migrations | 1.7 MB each | both insert the same recipes; the second is a no-op but replays on every fresh `db push` |
| Two `import_themealdb` migrations | 54 KB each | same |
| One 158-byte migration | — | an empty generated file |
| `package.json` + node tooling | small | the Firebase migration is done; is it still tooling or now history? |

`.gitignore` exists at 90 lines and does not mention `out/`, which is how it
got committed in the first place.

## Run

```powershell
powershell -ExecutionPolicy Bypass -File tools\clean_repo.ps1
```

It prints what it will touch at each step and only untracks `out/`
automatically — the deletions that need judgement it lists for you.

Then append `.gitignore.additions` to `.gitignore` and delete the additions file.

## What a Flutter repo should and should not carry

**Committed**
`lib/` `test/` `assets/` `fonts/` `android/` `supabase/` `tools/` `ml/` `docs/`
`pubspec.yaml` `pubspec.lock` `analysis_options.yaml` `.gitignore` `README.md`
`.github/`

`pubspec.lock` **is** committed for an application — it pins the exact
dependency versions your build was tested against. It is only excluded for
packages meant to be consumed by others.

**Not committed**
`build/` `.dart_tool/` `out/` `.env` `*.tflite` model weights, datasets,
`.idea/`, `.DS_Store`, anything a script regenerates.

## The judgement calls

**Duplicate migrations.** Keep the largest of each pair — it is the most
complete generation — and delete the rest. They are equivalent in effect
because every insert is guarded by a title check, so removing the extras
changes nothing except 3.4 MB and the confusion of finding two files that
claim to do the same thing.

**Node tooling.** `tools/*.js` exported your data out of Firebase. That job is
finished. If you might ever re-run it, keep it and say so in the README; if
not, removing it and `package*.json` removes a dependency tree nobody
installs.

**History rewrite.** Untracking `out/` stops it growing but leaves 7.5 MB in
history, so clones still download it. `git filter-repo` removes it properly but
rewrites history — anyone else with a clone must re-clone. Working alone on a
repo this size, untracking is enough.

## Keeping it clean

```powershell
git status --short          # before every commit
git count-objects -vH       # repo size over time
```

The rule that would have prevented all of this: **if a script produced it,
it does not belong in git.** The script belongs in git.
